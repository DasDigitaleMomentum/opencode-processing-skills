# Implementation Plan: Phase 5 - Declared Closure and Compact Dashboard

> Implements [Phase 5](../phases/phase-5.md) of [checkpoint-session-status-hardening](../plan.md)

## Approach

Make the shared checkpoint operation own the complete declared-lifecycle sequence. Extend `checkpoint` with the optional public `close_session=false`/internal `closeSession=false` argument while leaving all persisted record variants unchanged. Omission alone selects `false`; whenever the option is supplied, require a real boolean at every public/fallback/core boundary, pass that raw value through wrappers, and reject invalid values before any lifecycle or checkpoint append. Before writing, validate and construct the existing exact eight-field checkpoint plus exact four-field status records; then await one-line appends in physical `open` → checkpoint → optional `closed` order. Thus every checkpoint that returns successfully confirms `OPEN`, a final declared close returns with the log `CLOSED`, and the next ordinary checkpoint reopens it. Existing host-observed start/end writers remain additive and duplicate statuses remain valid. Closure is independent of `step_failed`, telemetry, checkpoint metrics, and work success.

Route the option through OpenCode's native tool and strict fallback executor, the Codex and Claude MCP schemas/runtimes and hook input wrappers, and Hermes' Python-native mirror. Preserve each adapter's established workspace and identity resolution: OpenCode and Claude subagents retain separate IDs, Codex remains session-level, and Hermes children still append under the resolved root-parent ID. Update the four installed heartbeat instruction paths with an explicit role distinction: a subagent sets `close_session=true` only on its final checkpoint immediately before returning a digest, summary, or handoff; a Maintainer/parent leaves it false unless deliberately ending the whole persisted session. No parent/child fields, hierarchy, or host-idle inference are added.

Turn the OpenCode persona instruction into an explicitly bounded managed block: keep `<!-- opencode-checkpoint-instruction -->` as its start marker and add `<!-- /opencode-checkpoint-instruction -->` as its end marker. Fresh ordinary personas receive that complete block once. On upgrade, leave an exact current block byte-for-byte unchanged; replace only the exact known pre-Phase-5 fragment with the new block while preserving every byte outside that exact match; and fail loudly without guessing when a non-symlink persona contains the start marker with any unknown/customized managed content. Symlinked personas remain untouched. This migration applies equally to retained generated variants and other ordinary personas that are not regenerated before the instruction pass.

Refactor only the watcher row projection and formatter around the exact columns `AGENT | NAME | AGE | STATE | CP | C/W/3 % | CONTEXT | DONE | CURRENT`. Keep session ID internally for file identity and deterministic tie-breaking, but render it nowhere in the dashboard; the detailed inspector remains unchanged and continues to show session identity and raw `next`. Group `OPEN` and `UNKNOWN` together first, `CLOSED` second, and `ERROR` last, sorting each valid group newest-first by latest physical event age and adding a blank separator between non-empty groups. Render checkpoint count separately and compact the existing chain/work/three-word percentages as a slash-separated value such as `100/50/100%` (`n/a/100/100%` when a metric has no denominator). Closed rows render `CURRENT` as `—`; unclosed rows retain the raw latest checkpoint `next`.

The watcher currently exposes `--stale-ms` and `CHECKPOINT_WATCH_STALE_MS` as documented, tested public compatibility inputs retained deliberately in Phase 2. Removing them is therefore not a clean backward-compatible change. Keep them accepted and validated as no-op compatibility inputs, but remove threshold/freshness wording from the dashboard banner and do not use either value in row loading, grouping, sorting, or formatting. Update help/docs to identify the retained inputs as compatibility-only rather than an active dashboard threshold.

## Implementation Steps

### Step 1: Centralize lazy open and declared close in the shared core

- **What**: Add `closeSession = false` to `checkpoint`. Apply the default only when the property is omitted/`undefined`; require every supplied value, including `null`, to be a real boolean before constructing or appending any record. Preserve the existing checkpoint creator and exact eight-field key order, and construct/validate all records before the first write. Reuse one captured clock instant so adding status records does not consume extra caller clock values or change the checkpoint timestamp. Sequentially append an exact `open` status line, the exact checkpoint line, and—only when `closeSession === true`—an exact `closed` status line. Keep one append operation per line, the current return object, path containment, and `appendSessionStatus` API unchanged. Propagate append errors without rewriting or rolling back already appended bytes.
- **Where**: `packages/checkpoint-core/src/index.js` (`checkpoint`, `createCheckpointRecord`, `createSessionStatusRecord`, `appendRecord` reuse); `packages/checkpoint-core/test/checkpoint-core.test.js`; focused status fixtures only if a static ordering fixture materially simplifies reader tests.
- **Authorized By**: Phase 5 Includes items 1–2; Acceptance Criteria 1–2 and 5; global plan decisions that every successful checkpoint confirms `open`, final declared close follows the checkpoint, physical order is authoritative, and exact record schemas/append-only logs remain compatible.
- **Why**: One shared sequence prevents OpenCode, Codex, and Claude wrappers from implementing subtly different ordering or status shapes and automatically turns resumed checkpoint-only logs from `UNKNOWN` to `OPEN`.
- **Considerations**: A default call now adds an idempotent `open` before its checkpoint but still returns the same feedback and yields exactly one checkpoint through `parseCheckpointJsonl`. An explicit `false` behaves identically; strings, numbers, `null`, arrays, and objects must fail before even the leading `open`. A close call must reduce to `CLOSED`; the next default call must physically append `open` then checkpoint and reduce back to `OPEN`. Validate labels, telemetry, metadata, identity, clock, and `closeSession` before any append. As with every append-only multi-write sequence, an I/O failure can leave a truthful prefix; never truncate or synthesize a compensating close. Sequential awaits guarantee each call's relative `open` → checkpoint → optional `closed` order but do not promise cross-process contiguity or locking; preserve the global plan's physical-order/no-stronger-ordering boundary. Status lines must not affect checkpoint count, adjacency, work, or three-word metrics, and `step_failed=true` must not suppress either requested lifecycle assignment.

### Step 2: Expose the backward-compatible option through all Node tools and wrappers

- **What**: Add optional `close_session` boolean with default `false` to OpenCode's native tool args and the Codex/Claude MCP `checkpoint` input schemas; leave `required` as `done` and `next`. Treat omission as false, but when the property is present validate that its raw value is a boolean at the OpenCode fallback executor, Codex MCP runtime, Claude `PreToolUse` rewrite, and Claude MCP runtime before any persistence call. Preserve and pass the raw boolean as core `closeSession`; never normalize with `=== true`, truthiness, or nullish fallback. Keep the real OpenCode native schema as the first boundary while retaining core validation as defense in depth. Preserve all identity, workspace, telemetry, metadata, feedback, JSON-RPC/tool-error shapes, and error behavior. Ensure Codex and Claude `PreToolUse` full-input rewrites retain the valid public `close_session` value while continuing to discard/replace only host-owned internal fields; an invalid Claude hook input fails through the existing hook stderr/nonzero path rather than emitting an `updatedInput`. Keep `checkpoint_path`, lifecycle hook registrations, host-observed start/end writers, and server queue/flush behavior unchanged.
- **Where**: `opencode/checkpoint-runtime.mjs` and fallback composition in `opencode/checkpoint-plugin.ts`; `codex/checkpoint-mcp-runtime.mjs`, `codex/checkpoint-hook.mjs`, `codex/checkpoint-mcp-server.mjs`; `claude/agent-checkpoint/server/checkpoint-mcp-runtime.mjs`, `claude/agent-checkpoint/scripts/checkpoint-hook.mjs`, `claude/agent-checkpoint/server/checkpoint-mcp-server.mjs`; corresponding OpenCode/Codex/Claude test files.
- **Authorized By**: Phase 5 Deliverable “Backward-compatible checkpoint API extension across shared core and all installed adapters”; Acceptance Criteria 2–3; plan Functional Requirement for the same optional argument across adapters and preserved identity/metadata/telemetry/path semantics.
- **Why**: The public tools use snake_case while the shared JavaScript core uses camelCase; every registration and hook rewrite must carry the same default without exposing host-owned IDs or adding persisted fields.
- **Considerations**: OpenCode's fallback helper must expose the same boolean/default schema as the native helper and its executor must enforce that schema for direct fallback calls. Codex's hook may preserve the raw public field for its MCP boundary, which must reject an invalid supplied value; Claude validates both its rewriting hook and MCP runtime. Codex remains one native-session log and Claude retains native parent/composite child IDs. Existing `session.created`, `SessionStart`, `SubagentStart`, and `SessionEnd` statuses can produce duplicate assignments; duplicates are intentionally idempotent. Assert schema shape, omitted/default false behavior, explicit false/true ordering, default reopen after a close, representative invalid values failing with no file/line append, and no leakage of `close_session` or internal fields into checkpoint/status records. Do not add a close hook or infer role from tool arguments.

### Step 3: Mirror sequencing and the optional argument in Hermes Python

- **What**: Extend `checkpoint(done, next, step_failed=False, close_session=False, ...)`, `_CHECKPOINT_SCHEMA`, and `_handle_checkpoint` with the optional boolean. Omission selects false; direct calls and handler-supplied values must reject every non-`bool` value before writing, and the handler must pass the raw supplied value rather than coercing it. After resolving the native invocation to its established root-parent log and telemetry slot, validate/create the exact eight-field checkpoint and exact status records before writing, reuse one clock instant, then append compact `open` → checkpoint → optional `closed` lines in physical order. Preserve `_on_session_start`'s observed `open`, `_on_subagent_start`'s mapping-only behavior, every lock-protected binding/telemetry invariant, and the exact Python mirrors of the six/eight/four-field validators.
- **Where**: `hermes/agent-checkpoint/agent_checkpoint.py` (`checkpoint`, `_CHECKPOINT_SCHEMA`, `_handle_checkpoint`, `_create_record`, `_create_status_record`, `_append_record` reuse); `hermes/test/test_agent_checkpoint.py` (`RegistrationTests`, `CheckpointWriteTests`, `FixtureParityTests`, binding/interleaving tests).
- **Authorized By**: Phase 5 Deliverable for the all-adapter API extension; Acceptance Criteria 1–3; global plan constraint preserving Hermes parent-owned logging and exact status/checkpoint schemas.
- **Why**: Hermes intentionally has no Node dependency, so its native writer must mirror the shared semantics rather than import the JavaScript core.
- **Considerations**: A child declaration continues to write the resolved parent `session_id`; do not create a child file or persist child/parent/role metadata. A parent checkpoint after a child-declared close appends `open` and reopens that shared row. Reject non-boolean direct Python input before any append, preserve compact UTF-8 JSON/key order and context feedback, and keep `checkpoint_path` write-free. Do not register a new host close hook or reinterpret `subagent_start`, `subagent_stop`, process exit, or telemetry as lifecycle evidence.

### Step 4: Install role-aware final-checkpoint instructions

- **What**: Update all four heartbeat fragments to describe `close_session=false`, explain that every checkpoint lazily confirms open, and add the exact role-aware final-call rule: subagents use `close_session=true` only on the final checkpoint immediately before a digest, summary, or handoff; Maintainers/parents keep it false unless intentionally ending the whole persisted session. Make explicit that a failed final work step may still close normally, closure is not success, interrupted/missing calls remain open, and a later checkpoint reopens. Preserve cadence, exact-three-word chaining, parallel-call, failed-step correction, context-pressure, and work-quality clauses. Bound the OpenCode source fragment with the existing start marker and exact new end marker `<!-- /opencode-checkpoint-instruction -->`. Change `install_opencode_checkpoint_instruction` to classify each non-symlink persona as: no marker → append the complete current managed block once; exact current start/end-bounded block → leave every byte unchanged; exact known pre-Phase-5 block → replace only those exact bytes with the current block; any other start-marker/managed-content shape → stop loudly and leave that persona unchanged. The exact legacy match is the complete checked-in pre-Phase-5 fragment bytes, from `<!-- opencode-checkpoint-instruction -->` through the final work-quality sentence and existing terminal newline; preserve all bytes before and after that exact substring during migration. Apply the same logic to retained generated variants and other ordinary personas, while continuing to skip symlinked personas without reading or changing their targets. Existing Codex/Claude/Hermes copy paths continue to replace only their ordinary non-symlink destination files.
- **Where**: `opencode/checkpoint-instruction.md`; `codex/checkpoint-instruction.md`; `claude/agent-checkpoint/instructions/checkpoint.md`; `hermes/agent-checkpoint/checkpoint-instruction.md`; `install.sh` (`install_opencode_checkpoint_instruction` managed-block classification/migration and existing adapter copy lists); instruction/install assertions in `opencode/test/checkpoint-plugin.test.mjs`, `codex/test/checkpoint-codex.test.mjs`, `claude/test/checkpoint-claude.test.mjs`, and `hermes/test/test_agent_checkpoint.py`.
- **Authorized By**: Phase 5 Includes item 3; Deliverable “Updated checkpoint instructions for final subagent closure”; Acceptance Criterion 3; global plan decision distinguishing subagent final closure from Maintainer session lifetime.
- **Why**: The optional flag is conservative only if callers know that routine parent checkpoints must not terminate a session and subagents declare closure immediately before returning control.
- **Considerations**: Keep the role rule conditional in shared fragments rather than editing canonical `agents/*.md`; OpenCode applies its marked fragment only to installed personas, while Codex/Claude/Hermes copy/inject their harness-local fragments. Do not treat start-marker presence alone as ownership: only the exact legacy block or exact current bounded block is installer-managed. Unknown/customized marked content is not silently overwritten, truncated, duplicated, or adopted; emit a path-specific recovery diagnostic and nonzero status instead. Tests must cover fresh append, exact-current byte idempotency, exact-legacy migration with unrelated prefix/suffix preservation, retained generated-variant and ordinary-persona upgrades, unknown/customized block refusal with unchanged bytes, and symlink preservation. Codex's pinned session-level identity and Hermes' root-parent identity mean a child declaration applies to the existing shared persisted row; document that limitation and rely on the next parent checkpoint's mandatory `open` rather than adding out-of-scope child metadata or files.

- **Where**: `packages/checkpoint-core/bin/checkpoint-watch.js` (`percent`/compact metric helper, `loadSessionRows`, comparator, adaptive widths, `formatDashboard`, `render`); `packages/checkpoint-core/test/checkpoint-watch.test.js`; cross-adapter watcher assertions in `hermes/test/test_agent_checkpoint.py`.

Use the existing one-decimal percentage normalization; a one-checkpoint row is `CP=1` with `n/a/100/100%`, and a status-only row is `CP=0` with `n/a/n/a/n/a`. Session ID remains available for file identity/ties and in the inspector but must not appear even when width is ample. Insert separators only between adjacent non-empty groups, not as labeled pseudo-rows. For an `ERROR` row, use neutral `CP`/metric/context fields, `DONE=read failed`, and the concise read/parse message in `CURRENT`; never treat `ERROR` as persisted lifecycle state.

### Mismatches / Notes

- The gated Phase 5 text says “append the checkpoint first and `closed` immediately afterward,” while the user-approved complete sequence also requires lazy `open` on every successful call. The concrete resulting physical sequence is therefore `open` → checkpoint → `closed` when true and `open` → checkpoint when false; this plan does not alter either exact record shape.
- `--stale-ms` and `CHECKPOINT_WATCH_STALE_MS` are not removable cleanly in this phase: Phase 2 deliberately retained them, `parseArgs` validates them, help and public installation docs advertise them, and tests assert their precedence/validation. They remain accepted compatibility-only no-ops, while all threshold/freshness presentation and semantics are removed from the dashboard.
- Codex has only native session-level identity on the pinned 0.131.0 surface, and Hermes deliberately maps child invocations to one root-parent persisted log. Consequently `close_session=true` always closes the adapter's existing persisted identity; it cannot create a separately visible closed child row for those two adapters without out-of-scope child identity/schema work. The next parent/session checkpoint immediately confirms `open` again. OpenCode and Claude retain separately attributed subagent logs.
- Existing host-observed writers remain valid: OpenCode creation, Codex `SessionStart`, Claude parent/subagent starts and parent `SessionEnd`, and Hermes new-parent start may duplicate the status assigned by a checkpoint. Physical-order reduction already defines duplicate assignments as idempotent and a later checkpoint-open as a resume/reopen.
- The watcher currently uses session ID as both a rendered fixed column and a deterministic tie-break. Phase 5 removes only rendering; keeping the internal ID for row identity and stable ties satisfies the hidden-ID requirement without weakening file isolation or inspector detail.
- The current dashboard exposes metric counts (`success/count`) in three columns. The compact dashboard keeps only CP plus percentages; detailed counts remain available from the unchanged inspector and analysis APIs, so no raw or derived information contract is removed from the detailed reader.
- `install.sh` already copies the shared core into OpenCode/Codex/Claude, the watcher into OpenCode support, every harness instruction, and the Hermes Python module. Its OpenCode instruction step is not refresh-capable for retained generated variants or other ordinary personas: marker presence alone currently yields `Present`. Execution must add the exact start/end-bounded migration chosen above, not defer that known change to testing; only the exact pre-Phase-5 block may be replaced, exact current content remains byte-stable, and unknown/customized marked content stops loudly while symlinked personas remain untouched.
- The current Node runtimes commonly derive boolean options with `=== true`, but `close_session` has a stricter accepted public contract: wrappers preserve the raw supplied value until the OpenCode fallback/core, Codex MCP, Claude hook/MCP, or Hermes direct/handler boundary verifies an actual boolean. Omission alone selects false, and invalid values cannot write even the leading lazy-open event.
- The exact Claude Code 2.1.170 and Hermes v0.19.0 binaries are absent on the current authoring host per completed Phase 4 evidence. The single verify command will continue to fail clearly at those two host checks here; it must pass in a suitable environment before the global plan can complete. Phase 5 does not resolve, waive, or broaden that blocker.
