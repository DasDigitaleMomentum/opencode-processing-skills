# Implementation Plan: Phase 2 - Real Desktop Installation and Model E2E

> Implements [Phase 2](../phases/phase-2.md) of [Claude Desktop Checkpoint](../plan.md)

## Approach

Treat Phase 2 as a gated live-validation and documentation slice over the reviewed Phase 1 source: first prove the approved app/configuration boundary without writing, then quiesce checkpoint readers/writers and run the unmodified global installer so its current YAML/environment/default resolution installs every enabled target. Preserve a private temporary pre-install Desktop-config snapshot only after the read-only gate passes, and use it to prove that installation adds exactly the reviewed Desktop registration while leaving unrelated semantic state unchanged. Fully restart the real Claude Desktop app, require observable connection and both real tools, send one literal-value prompt through the actual model UI, and validate the resulting closed lifecycle independently through raw JSONL, the existing inspector, the installed native watcher, the fresh MCP-log suffix, and source-to-installed byte comparison. After a zero-finding live implementation review, use the existing documentation workflow to update only the two Phase 2 docs; then run one complete final automated command and obtain the required final zero-finding review. Keep the permission-restricted config snapshot, safe external UI/log evidence copies, disposable workspace, and checkpoint JSONL outside the repository until that final review completes; remove them before staging and prove that none is present in the repository. The Primary then creates exactly one project-oriented final commit on the existing branch and pushes that same branch once without creating a branch or pull request.

## Implementation Steps

### Step 1: Close prerequisites and perform a read-only real-state preflight

- **What**: Confirm that the exact source to be installed is the zero-finding Phase 1 implementation-review state and already has a successful complete Phase 1 gate. Without creating a snapshot, directory, or other file, read `/Applications/Claude.app/Contents/Info.plist` and require both `CFBundleShortVersionString=1.24012.9` and `CFBundleVersion=1.24012.9`; independently inspect the existing `/Applications/Claude.app/Contents/Resources/app.asar` bytes and require embedded build metadata with `appVersion="1.24012.9"` and a 40-hex `commitHash` beginning `03c61d`. Require Node, scriptc, the expected Desktop config/adapter paths, and the Phase 1 Desktop files; reject symlinked config or adapter destinations/path components; parse `~/Library/Application Support/Claude/claude_desktop_config.json` without printing values and disclose only its root JSON type, sorted top-level key names, sorted MCP-server names, and whether `mcpServers` has the permitted object shape. Resolve the absolute Node executable and reviewed installed server destination, then run the source `configure-desktop.mjs --check` against those exact paths. Stop before every mutation on a version/revision mismatch, malformed/non-object/conflicting config, symlink, missing prerequisite, Phase 1 review/gate gap, or any unexpected disclosure requirement.
- **Where**: `/Applications/Claude.app/Contents/Info.plist`; `~/Library/Application Support/Claude/claude_desktop_config.json`; `~/Library/Application Support/Claude/agent-checkpoint/`; `claude-desktop/agent-checkpoint/configure-desktop.mjs`; Phase 1 source/review evidence.
- **Authorized By**: Phase 2 Prerequisites 1–4; Phase 2 Includes “Read-only preflight”; Acceptance Criterion 1; Plan scope-bounding app-version assumption and fail-closed configuration constraints.
- **Why**: The real installation is the first irreversible external-state boundary, so the approved app and safe semantic config shape must be established with the reviewed Phase 1 validator before any snapshot, disposable workspace, shutdown, copy, or config write occurs.
- **Considerations**: Do not print config values, command arguments from unrelated servers, environment contents, credentials, or existing log contents. A changed app build requires a new explicit user gate; it is not permission to broaden or weaken the E2E.

### Step 2: Quiesce, install every resolved target, and prove preservation/parity

- **What**: After Step 1 passes, create a mode-`0600` OS-temporary copy of the Desktop config and register cleanup for that copy plus later disposable artifacts. Using sanctioned app/process control, stop the live checkpoint dashboard and every running writer for the targets that the current installer resolution reports enabled; confirm they are quiescent. Run global `./install.sh` with the current `OPS_*` environment and repository `config.yaml`/defaults unchanged, retain its output only outside the repository, and require the reported enabled/disabled target set to equal the preflight resolution. Compare the installed Desktop core, runtime, server, and configuration-helper bytes to their reviewed source counterparts. Parse the installed config and require exactly `mcpServers.agent-checkpoint = {command: <absolute resolved Node>, args: [<absolute installed server>]}`; compare the pre/post JSON values after removing only that key and require semantic equality, proving unrelated top-level values, MCP servers, and Claude Code state were preserved. Stop on any installer fail-closed result; do not repair config manually or rerun with target overrides that change the resolved scope.
- **Where**: `install.sh`; current `config.yaml` and `OPS_*` resolution; `~/Library/Application Support/Claude/agent-checkpoint/`; `~/Library/Application Support/Claude/claude_desktop_config.json`; every destination printed as enabled by the installer.
- **Authorized By**: Phase 2 Includes “Global installation for every currently enabled target” and “Source-to-installed parity and exact Desktop registration readback”; Deliverable 1; Acceptance Criteria 2 and 8; Plan Functional Requirements 5–8 and Non-Functional Requirement 2.
- **Why**: The phase must install the exact reviewed source through the only authorized fail-closed path while proving both the Desktop adapter's byte identity and the additive configuration invariant, not merely trusting installer success text.
- **Considerations**: The temporary config copy can contain private values, so keep it permission-restricted, never print or commit it, and retain it through the final zero-finding review before deleting it in the pre-staging cleanup. Do not restart non-Desktop harnesses ahead of the newly installed dashboard; use the exact `Launch command` emitted by this installer run for the compatible reader.

### Step 3: Fully restart Desktop and establish fresh connection evidence

- **What**: Record only the pre-restart size/timestamp boundary of `$HOME/Library/Logs/Claude/mcp-server-agent-checkpoint.log`, not its contents. Fully quit Claude Desktop through the available sanctioned macOS app-control surface, prove no old Desktop process remains, relaunch `/Applications/Claude.app`, and prove a new app process is running. Inspect only the fresh MCP-log suffix after the recorded boundary for the `agent-checkpoint` server and require no relevant startup, stdio framing, JSON-RPC, or tool-registration failure. Through the actual restarted Desktop UI, verify that the local server is connected and that both exact tools `checkpoint` and `checkpoint_path` are available; record only safe visible evidence outside the repository. Stop if the real UI does not expose this evidence rather than substituting config, logs, direct MCP, Claude Code, or assumed selector/label state.
- **Where**: `/Applications/Claude.app`; `$HOME/Library/Logs/Claude/mcp-server-agent-checkpoint.log`; actual Claude Desktop connection/tool UI.
- **Authorized By**: Phase 2 Includes “Full Claude Desktop quit/restart, MCP connection/log inspection, and connector availability confirmation”; Deliverable 2; Acceptance Criterion 3; approved design Verification steps 2–3.
- **Why**: Config and installed bytes prove only setup; a fully new Desktop process, fresh server log, and observable real tool availability are required before the model-issued checkpoint can be attributed to the installed adapter.
- **Considerations**: Do not claim a UI control name, connector label, or log message that is not actually observed on the pinned app. No manual assertion substitutes for visible state.

### Step 4: Execute and validate the real Desktop-model checkpoint

- **What**: Create one disposable directory under the OS temporary root with no `.agent-checkpoints/`, resolve its literal absolute path, and choose one filesystem-safe, conversation-stable `claude-desktop-live-<UTC timestamp>-<random suffix>` session ID. In the real restarted Desktop conversation, send a prompt containing those resolved literals and requiring exactly one final `checkpoint` with `done="Desktop MCP verified"`, `next="Live validation complete"`, `step_failed=false`, and `close_session=true`; wait for the real model/tool result and use the one permitted manual action only if Desktop presents its normal tool-permission dialog. Require the selected JSONL to contain exactly three physical records in order (`open`, one exact eight-field checkpoint, `closed`) with the chosen session ID, requested values, and `context_used`, `agent`, and `session_title` all `null`. Run the source `checkpoint-inspect` against that selected absolute path and require `CLOSED`, the exact payload, completed work, unknown/null-rendered metadata, and one fully three-word-compliant checkpoint. From the disposable workspace run the installed native `$HOME/.local/bin/checkpoint-watch --once` and require the same real row to show `CLOSED`, `CP=1`, the expected three-word `DONE`, and no current work. Finally inspect the post-call MCP-log suffix and repeat Desktop source-to-installed byte parity; stop on any relevant tool/protocol error or evidence mismatch.
- **Where**: Actual Claude Desktop model conversation; OS-temporary workspace; its `.agent-checkpoints/<session-id>.jsonl`; `packages/checkpoint-core/bin/checkpoint-inspect.js`; installed native `$HOME/.local/bin/checkpoint-watch`; fresh Desktop MCP-log suffix; installed Desktop adapter.
- **Authorized By**: Phase 2 Includes “real model-issued final checkpoint” and “Inspector and watcher validation”; Deliverables 3–5; Acceptance Criteria 4–6 and 8; Plan Definition of Done 3–5; approved design Verification steps 4–6.
- **Why**: Only a real Desktop model call followed by persisted, reader-independent, log-clean evidence proves the approved end-to-end boundary; direct protocol calls and synthetic logs are explicitly excluded.
- **Considerations**: Substitute the resolved path and ID as literal prompt text rather than shell-variable tokens. Do not make a direct MCP call, fabricate JSONL, use Claude Code, or accept a model response without the real tool result. Keep the permission-restricted disposable workspace/JSONL and safe external UI/log evidence copies available through both the first review and the final zero-finding review; never add them to the repository, and remove them only in the pre-staging cleanup after the final review.

### Step 5: Pass live review, then update only the ordered Phase 2 docs

In the installation guide, add the independently enabled Desktop target and locations, config/environment controls, full-quit/restart and MCP-log path, exact explicit `workspace_root`/stable `session_id` inputs, honest-null telemetry, conflict/symlink behavior, and the pinned real-model E2E boundary. In the harness matrix, add Claude Desktop's MCP-only identity/workspace inputs, `open` → checkpoint → declared `closed` lifecycle, null `context_used`/`agent`/`session_title`, and the pinned live-verification boundary; update only directly affected cross-adapter counts/wording. Keep the focused Desktop README and `config.yaml.example` as Phase 1 artifacts, and do not edit the design status or add a separate live-evidence artifact.
- **Where**: `docs/installation.md`; `docs/agent-checkpoint-heartbeat.md`.
- **Authorized By**: Phase 2 Includes “Post-review incremental updates”; Deliverable 6; Acceptance Criterion 7; Plan Functional Requirement 11 and Definition of Done 6; the plan-review-remediated four-artifact documentation boundary.
- **Why**: The user ordered existing project documentation to be updated only after implementation review, and these are the only deferred artifacts authorized to turn the proven live behavior into durable user guidance.
- **Considerations**: Describe only behavior proven on Claude Desktop 1.24012.9 (`03c61d`); include no user config values, logs, temporary paths/session IDs, screenshots, credentials, or unverified UI labels. Do not broaden into root README, changelog, module inventory, design-status, or release notes.

### Step 6: Run the single final gate and obtain final zero-finding review

- **What**: From the final source/docs state, recheck safe Desktop registration shape, clean fresh MCP-log suffix, and Desktop adapter source-to-installed parity, then run the single Primary Verify Command below exactly once. After it passes, request a fresh independent implementation review of the complete Phase 2 live-evidence and documentation state while the permission-restricted config snapshot, disposable workspace/JSONL, and safe external UI/log evidence copies remain available for direct inspection. Remediate and re-run the same single command only if a finding changes source/docs, and continue independent review until no findings remain. Hand the zero-finding state to the Primary for the cleanup and delivery step below; do not perform Git operations in this verification/review step.
- **Where**: Installed Desktop config/adapter/log; complete repository test suites; `docs/installation.md`; `docs/agent-checkpoint-heartbeat.md`; Phase 2 final implementation-review artifact owned by the review workflow.
- **Authorized By**: Phase 2 Acceptance Criteria 8–9; Plan Definition of Done 1–2 and 7–8; Plan Testing Strategy; global constraint that all workflow gates precede the one final commit and push.
- **Why**: The final state needs one broad reproducible repository proof and a reviewer independent of the implementation/documentation work before delivery can proceed.
- **Considerations**: This step authorizes verification and review, not staging, committing, pushing, branch creation, or a pull request. Any source/docs remediation invalidates the prior final-command result and installed parity, so rerun the same command and re-establish parity before re-review. Do not clean up the external live evidence needed by the final reviewer in this step.
